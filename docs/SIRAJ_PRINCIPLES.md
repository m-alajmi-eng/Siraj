# مبادئ سراج الهندسية (SIRAJ Engineering Principles)

هذه الوثيقة مرجع ثابت يُقاس عليه أي قرار معماري مستقبلي في سراج، بدل
الاعتماد على الانطباع اللحظي أو تغيّر الرأي مع الوقت. نتاج مراجعة معمارية
ثلاثية الأطراف (المطوّر، مراجع معماري، Claude) بتاريخ يوليو 2026.

---

## المبدأ المظلة

### Evolution Over Perfection
نفضّل نظاماً بسيطاً يمكن تطويره تدريجياً على نظام مثالي نظرياً يصعب
إطلاقه وصيانته. كل مبدأ لاحق في هذه الوثيقة هو تطبيق لهذا المبدأ الأساسي:
- لا نبني Backend قبل الحاجة الفعلية.
- لا نضيف Repository Layer قبل الحاجة الفعلية.
- لا نضيف محرك بحث قبل الحاجة الفعلية.
- لا نضيف AI قبل الحاجة الفعلية.
- لا نضيف Microservices قبل الحاجة الفعلية.
نبني بطريقة تسمح بالتطور عندما تظهر الحاجة الحقيقية — لا قبلها.

## المبادئ

### 1. Offline First
كل ميزة يجب أن تعمل دون اتصال إنترنت حيثما سمحت طبيعة المحتوى والترخيص.
انظر ADR-003 للتصنيف الدقيق (مُضمَّن / يُنزَّل عند الطلب / مُتزامن / سحابي).

### 2. Privacy First
لا نجمع بيانات شخصية أكثر من الضروري. لا نتتبّع أبداً أي محتوى ديني محدد
يقرأه المستخدم (أي آية، أي دعاء، أي كتاب) — هذا خصوصية دينية شخصية. نتتبّع
فقط استخدام الميزات على مستوى عام (فتحت شاشة كذا، لا قرئت آية كذا).

### 3. Flutter Only
كود واجهة واحد لكل المنصات. لا Native منفصل لكل نظام تشغيل إلا لضرورة
تقنية قصوى غير متوفرة عبر Flutter (انظر ADR-001).

### 4. Feature-based Architecture
كل ميزة (`lib/features/<name>/`) تحمل طبقاتها الخاصة (`domain/entities`,
`data/datasources`, `presentation/providers`, `presentation/screens`) بشكل
مستقل عن الميزات الأخرى. هذا يسمح بإضافة/تعديل/حذف ميزة كاملة (كما حدث
فعلياً عند استبدال ميزة "الحديث" بـ"المكتبة الشاملة") دون التأثير على
باقي التطبيق.

### 5. No Premature Optimization — Measure Before Optimizing
لا نُحسّن أداء أو بنية لم تُقَس فعلياً. كل تحسين مبني على رقم حقيقي
(زمن استجابة، حجم بيانات، عدد استخدام) لا تخمين نظري.

### 6. Minimize Vendor Lock-in
كل مصدر بيانات خارجي (Supabase، IslamHouse، alquran.cloud، Firebase) يُعزل
خلف طبقة `datasource` مخصصة تستدعيها `provider` واحدة. استبدال المصدر
يتطلب تعديل طبقة الـ datasource فقط، لا الشاشات. انظر أيضاً خطة الهجرة
النظرية في نهاية هذه الوثيقة.

### 7. Simplicity Over Cleverness
نفضّل الحل الأبسط والأوضح على الحل "الذكي" المعقّد، خاصة أن سراج يُصان
من مطور واحد. وضوح الكود أهم من إيجازه.

### 8. Accessibility & Localization by Default
كل ميزة جديدة تُبنى بدعم كامل لكل اللغات المتوفرة (15 لغة حالياً) ودعم
RTL/LTR منذ اليوم الأول، لا كإضافة لاحقة. هذا موثق فعلياً كممارسة قائمة
في كل ميزة بُنيت (القرآن، الأذكار، البوابة، المكتبة الشاملة).

### 9. Security by Design
Row-Level Security تُراجَع مع كل جدول Supabase جديد، لا مرة واحدة فقط.
قائمة تحقق ثلاثية عند كل جدول يمس بيانات مستخدم:
- هل الجدول له RLS مفعّلة؟
- هل السياسة تمنع قراءة/تعديل بيانات مستخدم آخر؟
- هل اختُبر هذا فعلياً بحساب ثانٍ؟

### 10. Religious Content Accuracy Over Speed
أي قرار تقني (تخزين مؤقت، سقوط لغوي، تحديث تلقائي) يمسّ نصاً دينياً
(قرآن، حديث، تفسير، شهادة، دعاء) يُراجَع بعناية أكبر من أي كود آخر في
المشروع، حتى لو أبطأ ذلك التطوير. أي نص ديني غير مؤكد المصدر يُعلَم صراحة
بحقل `needs_verification` في البيانات ولا يُطلَق للجمهور دون مراجعة.

## Definition of Done (معيار انتهاء أي ميزة)

قبل اعتبار أي ميزة "مكتملة":
- [ ] تعمل Offline إن سمحت طبيعة المحتوى (مبدأ 1).
- [ ] تدعم RTL وLTR بشكل صحيح.
- [ ] تدعم كل اللغات الـ15 المتوفرة (لا نصوص إنجليزية/عربية ثابتة متبقية).
- [ ] لا تكسر إمكانية الوصول (Accessibility) الأساسية.
- [ ] لها معالجة أخطاء مناسبة (لا شاشة بيضاء أو عطل عند فشل الشبكة).
- [ ] لا تُخفّض أداء التطبيق بشكل ملحوظ (يُقاس، لا يُخمَّن).
- [ ] اختُبرت يدوياً على الأقل بلغة عربية ولغة أخرى غير لاتينية.
- [ ] إذا احتوت منطقاً حساساً (خاصة سقوط لغوي أو تحويل بيانات)، لها Unit Test.
- [ ] إذا عرضت نصاً دينياً، تحقق من مبدأ 10 أعلاه.

## استراتيجية الإصدارات (Versioning)

- **إصدار التطبيق:** Semantic Versioning قياسي (`MAJOR.MINOR.PATCH`) في `pubspec.yaml`.
- **تغييرات قاعدة البيانات:** ملف SQL migration واحد لكل تغيير هيكلي، محفوظ
  في `supabase/migrations/` بترقيم تسلسلي بالتاريخ عبر Supabase CLI.
- **تغييرات ملفات JSON للمحتوى:** كل ملف `assets/data/*.json` يحمل
  `_meta.schema_version` رقمياً، يُرفَع فقط عند تغيير **بنية** الملف
  (لا محتواه). أي تغيير بنيوي يجب أن يكون **إضافياً** (حقول جديدة اختيارية)
  لا **كاسراً** (حذف/إعادة تسمية حقل) إلا مع رفع MAJOR version للتطبيق.

## خطة الهجرة النظرية (Migration Strategy)

هذه خطة **مكتوبة لا مُنفَّذة** — تفعَّل فقط عند ظهور سبب فعلي موضوعي
(انظر معايير إعادة التقييم في ADR-002).

**Supabase → أي بديل (AWS RDS / Google Cloud SQL):**
1. `pg_dump` كامل لقاعدة البيانات (Postgres قياسي، لا تنسيق خاص بـ Supabase).
2. استعادة على Postgres الجديد.
3. إعادة كتابة سياسات RLS يدوياً (لا تُصدَّر تلقائياً بين المزودين).
4. إعادة تكوين Auth — **الجزء الأصعب دائماً**: نقل مستخدمين موجودين يتطلب
   أداة هجرة مخصصة أو إعادة تسجيل، فيُخطَّط له بعناية خاصة عند الحاجة الفعلية.

**معيار تفعيل هذه الخطة (لا رقم تعسفي كـ"بعد سنتين"):**
- Supabase يرفع الأسعار بشكل غير مبرَّر لحجم استخدام سراج الفعلي، أو
- تظهر حاجة تقنية فعلية غير متوفرة في Supabase إطلاقاً.

## معايير الترقية المعمارية (بدل أرقام مستخدمين تعسفية)

نراقب هذه المؤشرات الفعلية (عبر Crashlytics + Supabase Dashboard) بدل
التخطيط لأرقام مستخدمين مفترضة:
- متوسط زمن الاستجابة الفعلي للاستعلامات.
- تكلفة التشغيل الشهرية الفعلية.
- حجم قاعدة البيانات الفعلي.
- عدد الاستعلامات اليومية الفعلي.
- معدّل الأعطال المُبلَّغ عنه (Crashlytics).
- زمن البحث المحلي الفعلي (هل أصبح ملحوظاً على جهاز ضعيف؟).

عندما يتجاوز أي مؤشر عتبة مزعجة فعلياً (لا نظرياً)، يُفتح نقاش معماري
مخصص لتلك النقطة تحديداً — لا تغيير شامل استباقي.
