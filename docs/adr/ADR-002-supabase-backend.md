# ADR-002: الاعتماد على Supabase كخلفية (Backend)

**الحالة:** مُعتمَد

## المشكلة
سراج يحتاج تخزين بيانات (تفسير القرآن حالياً، ومستقبلاً بيانات مستخدم مثل
العلامات المرجعية والملاحظات) مع مصادقة مستخدمين، دون تحمّل عبء بناء وصيانة
خادم خلفي كامل من الصفر بموارد مطور واحد.

## القرار
اعتماد **Supabase** (Postgres مُدار + Auth + Row-Level Security + Storage
+ Edge Functions عند الحاجة) كخلفية وحيدة، دون بناء خادم وسيط (BFF/NestJS/FastAPI)
في هذه المرحلة.

## سبب القرار
- Postgres قياسي بالكامل تحت الغطاء، ما يعني إمكانية تصدير البيانات
  (`pg_dump`) والهجرة لاحقاً دون قفل كامل على المزوّد.
- Row-Level Security يوفر تحكم صلاحيات على مستوى قاعدة البيانات مباشرة،
  فيغني عن معظم منطق "الحماية" الذي قد يُبنى في خادم وسيط.
- Edge Functions (عند الحاجة الفعلية لمنطق حسّاس لا يُعبَّر عنه بـ RLS)
  تقدّم 90% من فائدة BFF دون تشغيل خادم منفصل.
- بناء NestJS/FastAPI الآن يضيف عبء تشغيل وصيانة وأمن خادم إضافي بلا فائدة
  ملموسة لحجم الاستخدام الحالي (صفر إلى آلاف المستخدمين).

## متى نعيد تقييمه
- عند ظهور **حاجة تقنية فعلية غير متوفرة في Supabase إطلاقاً** (لا نظرية).
- إذا رفع Supabase الأسعار بشكل غير مبرَّر لحجم استخدام سراج الفعلي.
- عند الحاجة لمنطق عمل معقّد متعدد الخطوات لا يمكن التعبير عنه بدالة Edge
  واحدة بشكل معقول — عندها نبدأ بـ Edge Functions إضافية أولاً، لا بخادم كامل.
- انظر أيضاً: خطة الهجرة النظرية في هذا المستند (قسم لاحق) لتفاصيل الانتقال
  عن Supabase إن استدعى الأمر مستقبلاً.
