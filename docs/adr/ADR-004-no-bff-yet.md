# ADR-004: عدم بناء Backend-for-Frontend (BFF) في هذه المرحلة

**الحالة:** مُعتمَد

## المشكلة
هل نحتاج طبقة خادم وسيطة صغيرة (BFF) بين Flutter وSupabase/مصادر المحتوى
الخارجية (IslamHouse، alquran.cloud)، لتقليل الارتباط المباشر بمزوّد واحد
وتنظيم منطق العمل الحسّاس؟

## القرار
لا نبني BFF منفصلاً (كخادم Node/FastAPI مستقل) في هذه المرحلة. عند ظهور
حاجة فعلية لمنطق حسّاس لا يُعبَّر عنه بسهولة عبر Row-Level Security في
Supabase، نستخدم **Supabase Edge Function واحدة مخصصة لتلك الحالة**، لا
طبقة خادم كاملة.

## سبب القرار
- بناء وصيانة خادم منفصل (حتى لو "صغيراً") يضيف: نشر (deployment)، مراقبة،
  تحديثات أمنية، وتكلفة تشغيل مستمرة — كل هذا بلا فائدة ملموسة لحجم
  الاستخدام الحالي (ما قبل الإطلاق).
- Edge Functions تعيش داخل بنية Supabase نفسها، فلا تضيف مزوّداً جديداً
  للاعتماد عليه، وتُكتب/تُنشر بأمر واحد دون بنية تحتية إضافية.
- معظم الأسباب الشائعة لطلب BFF (rate limiting، caching، تنظيم منطق) قابلة
  للتحقيق عبر ميزات Supabase المدمجة (RLS، Postgres functions، Edge
  Functions) دون خادم منفصل.

## متى نعيد تقييمه
- إذا احتجنا **دمج بيانات من أكثر من مصدر خارجي حقيقي في استجابة واحدة**
  بمنطق أعمال معقّد يتجاوز قدرة دالة واحدة معقولة الحجم.
- إذا احتجنا معدل استدعاء (rate limiting) دقيقاً عبر عدة خدمات لا يمكن
  التعبير عنه ببساطة داخل Supabase.
- عند تفعيل مساعد التلاوة مستقبلاً (انظر ADR-005)، الخدمة الجديدة (Whisper
  على GPU) ستكون خدمة **منفصلة تماماً** لا BFF عام — طبقة إضافية مخصصة
  لتلك الميزة وحدها، لا حلاً شاملاً لكل التطبيق.
