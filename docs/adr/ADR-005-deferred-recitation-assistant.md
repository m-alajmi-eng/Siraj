# ADR-005: تأجيل مساعد التلاوة (Recitation Assistant) لما بعد الإطلاق

**الحالة:** مُعتمَد

## المشكلة
كانت هناك خطة لبناء ميزة "مساعد التلاوة" تستخدم نموذج تحويل صوت-لنص مبني
على Whisper (تحديداً FaisaI/Tadabur-Whisper-Small، مُدرَّب على تلاوة القرآن)
لتصحيح تلاوة المستخدم وتتبع تقدّمه. الميزة تتطلب معالجة على GPU (سيرفر
سحابي)، وليست مجانية التشغيل.

## القرار
تأجيل بناء أي جزء من هذه الميزة (واجهة أو خلفية) إلى ما بعد الإطلاق الأول
لسراج، دون بناء أي "أساس" مسبق لها الآن.

## سبب القرار
- التكلفة التشغيلية حقيقية ومستمرة (تُدفع حسب الاستخدام الفعلي بالثانية/
  الدقيقة على خدمات مثل RunPod، لا اشتراكاً ثابتاً)، وتتصاعد مع نمو عدد
  المستخدمين — قرار مسؤول لمشروع خيري يتطلب معرفة حجم الاستخدام الفعلي
  أولاً قبل الالتزام بتكلفة مستمرة.
- شكل الـ API النهائي (صيغة الطلب/الاستجابة، حدود الحجم، دعم الـstreaming)
  غير محدَّد بعد، وبناء واجهة أو "أساس" كود الآن يعني على الأرجح إعادة
  كتابته لاحقاً عند اتضاح الشكل الفعلي — عمل مُهدر.
- كل ساعة/سطر كود يُبنى الآن لميزة غير مُفعَّلة يزيد تعقيد الصيانة لمطور
  واحد، ويصعّب مراجعة الكود لاحقاً (كود "ميت" لا يُختبر ولا يُستخدم).
- الأولوية الحالية هي إكمال الميزات الأساسية اللازمة للإطلاق (قارئ السور،
  مراجعة الشاشات، اختبار الصوت)، لا ميزة إضافية اختيارية.

## متى نعيد تقييمه
- بعد الإطلاق الأول وجمع بيانات استخدام حقيقية (عدد مستخدمين نشطين،
  الميزات الأكثر طلباً).
- عند اتخاذ قرار بخصوص مزوّد الاستضافة (سيرفر خاص مقابل RunPod/مشابه)
  بناءً على تقدير تكلفة واقعي لحجم الاستخدام الفعلي حينها.
- التصميم المستقبلي المتفق عليه: خدمة AI **منفصلة تماماً** عن تطبيق
  Flutter (لا queue في البداية، تواصل REST بسيط: رفع صوت → استقبال نص
  وتقييم)، تُضاف كميزة مستقلة دون تعديل جوهري على بنية التطبيق الحالية.
